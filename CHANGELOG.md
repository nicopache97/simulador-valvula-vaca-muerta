## v0.7.0 — EP-06: Backend RBAC + auditoría + exportación `apps/server` (2026-10-20)

- **REQ-NFUN-SEC-01 (refinamiento EP-06)** — RBAC real de servidor en `apps/server` (Hono + **better-sqlite3**; schema creado al iniciar, sin migraciones — decisión "simple, vago"): tabla `users` sembrada con los 3 perfiles ISA/IEC 62443 (`operator`/`technician`/`engineer`, contraseña demo `vaca2026`, hash sha256+sal por usuario) y tabla `audit_log` (ts ISO, user, rol, acción, detalle JSON, resultado OK/DENIED). Auth mínima correcta sin dependencias extra: `POST /api/login` emite un **token de sesión firmado HMAC-SHA256** (`base64url(payload).sig`, análogo a un JWT mínimo; TTL 8 h = turno; clave `SIM_SECRET`), verificado con `timingSafeEqual`.
- **Endpoints** — `POST /api/login` (401 `ERR_INVALID_CREDENTIALS` si falla); `POST /api/calibrate` (401 `ERR_UNAUTHORIZED` sin Bearer; OPERATOR ⇒ 403 `ERR_ACCESS_DENIED`; TECHNICIAN/ENGINEER ⇒ 200 `{status:'ok'}`); `GET /api/audit` (solo ENGINEER; 403 para otros roles); `POST /api/export` (`{format:'csv'|'json', snapshots: SimSnapshot[]}` ⇒ 200 `text/csv` con cabecera de columnas y una fila por snapshot, celdas objeto/vector serializadas, o JSON idéntico al pedido; 400 si `snapshots` vacío; sin auth, uso portable tipo host loader); `GET /api/health` inalterado. Toda calibración queda en `audit_log`, **incluidos los rechazos** (TC-NFUN-SEC-01).
- **REQ-NFUN-PORT-01 (refinamiento EP-06)** — El backend es autocontenido: `node dist/index.js` corre nativo en Node ≥ 20 (única dependencia nativa better-sqlite3, prebuilds; sin software propietario). Configurable por env: `SIM_DB` (default `data/sim.db`, creado con `mkdirSync` al arrancar) y `PORT` (default 3001).
- **Integración con el front** — `SimProvider` autentica el rol activo contra `POST /api/login` al cambiar de usuario (proxy `/api` → `:3001` ya existía en Vite) y el comando `calibrate` pasa primero por `POST /api/calibrate`: un 403 se muestra como `ERR_ACCESS_DENIED` en la pestaña Calibración AMS ("…Rechazo registrado en auditoría") y **no** llega comando al worker; un 200 postea al worker con estado "Comando AMS autorizado por el servidor…". **Fallback offline**: si el server no responde (o `fetch` no existe), se recae en la validación local de rol (Operador ⇒ `ERR_ACCESS_DENIED` modo offline) sin romper la simulación. Con server online el botón Aplicar del Operador se habilita a propósito: es el servidor quien rechaza y audita (offline sigue deshabilitado, TC-UI-02 intacto).
- **Tests (Vitest, 12 nuevos en `@sim/server` + 2 nuevos en web; 50 verdes en server+web, 92 en total):** TC-NFUN-SEC-01 completo como test de integración (login OPERATOR → calibrate `{urv:40}` → 403 `ERR_ACCESS_DENIED` → registro DENIED en `audit_log` con detalle del comando), login de los 3 perfiles + rechazo de credenciales, 401 sin token (sin registro de auditoría), TECHNICIAN/ENGINEER calibran con registro OK, `GET /api/audit` solo ENGINEER (403 OPERATOR/TECHNICIAN, 401 anónimo), TC-NFUN-PORT-01 (health 200, export CSV con cabecera + filas, JSON idéntico, 400 con snapshots vacíos), y en web (fetch mockeado): Operador online clickea Aplicar ⇒ `ERR_ACCESS_DENIED` en pantalla y cero comandos al worker; Técnico online ⇒ comando al worker + estado "autorizado por el servidor". **Verificación standalone real:** `node dist/index.js` levantado con `SIM_DB=/tmp/... PORT=3210` y ejercitado con curl (health → login ×3 → calibrate 403/200 → audit → export CSV) — comportamiento conforme de punta a punta.
- **Decisiones registradas:** better-sqlite3 (sync, prebuilds Node 20/22) sin ORM — Drizzle se descartó: el schema son 2 tablas y el proyecto manda "mínimo código que cumpla el REQ"; token HMAC propio en lugar de JWT/jose — misma garantía (firma + expiración + comparación constante) con cero dependencias; seed por defecto con credenciales demo documentadas (simulador de entrenamiento; `SIM_SECRET` permite endurecer); export sin autenticación porque REQ-NFUN-PORT-01 lo usa como salida portable del host loader, no como operación sensible.

## v0.6.0 — EP-05: FMU FMI 3.0 Co-Simulation en WASM `packages/fmu` (2026-10-20)

- **REQ-GEN-02 (refinamiento EP-05)** — El núcleo de simulación se exporta como FMU de Co-Simulación FMI 3.0 compilada a WebAssembly con **AssemblyScript** (`asc`), el único código fuera del TS vanilla del proyecto: paquete nuevo `@sim/fmu` (`assembly/index.ts`) con el subconjunto de API FMI 3.0 `fmi3InstantiateCoSimulation` / `fmi3FreeInstance` / `fmi3EnterInitializationMode` / `fmi3ExitInitializationMode` / `fmi3SetFloat64` / `fmi3GetFloat64` / `fmi3SetInt32` / `fmi3GetInt32` / `fmi3DoStep`. La física es un **port fiel del engine de `@sim/physics`** (mismos defaults y orden de operaciones en f64 — verificado bit-exact contra el engine TS, |diff| = 0 en 100 pasos), no una copia divergente: válvula (histéresis/fricción stick-slip/zona muerta), caudal IEC 60534-2-1 con cavitación crítica, transmisor TB→AI y PID, con los 4 escenarios de proceso.
- **Empaquetado .fmu** — `modelDescription.xml` (fmiVersion 3.0.2, `CoSimulation` con `canHandleVariableCommunicationStepSize`, UnitDefinitions bar/psi/m³/h/s, `instantiationToken` fijo) + `binaries/wasm32/ValvulaTransmisor.wasm`, empaquetado con `adm-zip` (sin depender del `zip` del sistema). El XML se validó contra el **XSD oficial FMI 3.0.2** (12 archivos del tag `v3.0.2` de modelica/fmi-standard, vendidos en `packages/fmu/schema/` bajo licencia BSD-2-Clause) con `xmllint`. Artefacto en `packages/fmu/dist/` (gitignored); build reproducible con `npm run build:fmu` (raíz) o `npm run build:fmu -w @sim/fmu` (compila `asc` y empaqueta).
- **Mapa de variables (value references)** — entradas: `spBar` (vr 1, Float64 [bar]) y `scenario` (vr 2, Int32: 0 normal / 1 cavitacion / 2 falla_sensor / 3 transitorio_p1); parámetros (vr 10–26, `variability="fixed" initial="exact"` con los defaults de `createSimulation`: supplyBar, vesselNominalBar, qDemandNominal, capacity, cv, fl, fricción, zona muerta, txTau, kp, ti, measure, faultAtSec, stepAtSec, stepToBar, rampBarPerSec, rampToBar); salidas (vr 30–41): pvPercent, valveOpening, pAct, flow, choked (Float64 0/1 por el subconjunto Float64/Int32), quality (Int32 0/1/2), pvBar, p1Bar, p2Bar, dpChokedBar, pidOutPercent, time. `choked`/`quality` documentan su codificación en el atributo `description` del XML.
- **Adaptaciones ABI WASM (decisión registrada)** — sin strings ni callbacks en la firma: `fmi3Instance` = índice i32 de un registro de instancias; los arrays `valueReferences[]`/`values[]` de la C-API se intercambian por **memoria lineal en offsets de scratch exportados** (`SCRATCH_VR`/`SCRATCH_F64`/`SCRATCH_I32`), análogo a los punteros C; `fmi3DoStep` omite `currentCommunicationPoint` (el reloj lo lleva la instancia, como el engine) y no implementa earlyReturn (REQ-FUN-SIM-02 fuera de alcance según AGENTS.md §4). Los inputs `spBar`/`scenario` son *pending inputs* consumidos en el próximo paso, espejando `SimulationInputs` del engine.
- **Tests (Vitest, 11 nuevos en `@sim/fmu`; 79 verdes en total):** TC-GEN-02 — carga del `.fmu` desde JS (ZIP → XML + WASM), metadatos (layout wasm32, atributos raíz FMI 3.0.2, VRs únicos, ModelStructure ⊆ variables, causalidades entrada/salida/parámetro), **validación XSD con xmllint** (skip si no está disponible), instanciación + lifecycle, lectura de parámetros con su `start` y de salidas finitas **usando las VRs leídas del XML contra el binario**, 100 pasos `fmi3DoStep` con rampa de SP a dt = 10 ms comparados paso a paso contra el engine TS (< 1e-9 relativo; medido bit-exact), ciclo `falla_sensor` vía `fmi3SetInt32` (quality → BAD_SENSOR_FAILURE, PV retenido, ≡ engine), `fmi3FreeInstance` → operaciones devuelven `fmi3Error`, VR desconocido → `fmi3Error`.
- **Validación del XML:** `xmllint --schema packages/fmu/schema/fmi3ModelDescription.xsd` → "validates" (XSD oficial FMI 3.0.2). **FMPy descartado**: pip/python disponibles pero FMPy no soporta FMUs WASM (el binario wasm32 no lo ejecuta; el contrato TC-GEN-02 se verifica con los tests JS) y la validación XSD oficial es estrictamente más fuerte para el XML; xmllint + XSD vendido mantiene la verificación hermética y offline.
- **Decisiones registradas:** `binaries/wasm32/` (módulo wasm32 core instanciable desde JS, según TC-GEN-02) en lugar del perfil `wasm32-wasip2` del draft FMI-LS-WASM (WebAssembly Component Model + WIT, no soportado por AssemblyScript ni requerido por el TC); inputs con `pending` semantics; parámetros aplicados al salir de InitializationMode (re-`createSimulation`), seteables también después (tunables).
- **Métricas:** 10 000 pasos de `fmi3DoStep` + lectura de las 11 salidas en 11.6 ms de wall-clock en Node 20 (≈ 1.2 µs/paso, factor ≈ 8 300× tiempo real; presupuesto REQ-NFUN-PERF-01: < 20% del paso). Diferencia numérica FMU vs engine TS: **0** (idéntica aritmética f64).
- **Docs:** REQ-GEN-02 (refinamiento EP-05) + TC-GEN-02 en `docs/requerimientos.md` con versión v0.6.0; `@sim/fmu` v0.6.0; raíz a v0.6.0; script raíz `build:fmu`.
- REQ/TC agregados: REQ-GEN-02 (refinamiento EP-05), TC-GEN-02.

## v0.4.0 — EP-03: Worker de simulación en tiempo real + contrato compartido (2026-10-20)

- **REQ-GEN-01 (refinamiento)** — Engine de orquestación puro en `@sim/physics` (`src/engine.ts`): `createSimulation(config)` / `stepSimulation(sim, inputs, dt)` / `toSnapshot(sim)`. Cierra el lazo completo SP → PID (P+I, anti-windup) → posicioner 3–15 psi → dinámica de vástago → caudal IEC 60534-2-1 → vasija (dV/dt con demanda fija) → transmisor TB→AI → PV. Escenarios: `normal`, `cavitacion` (rampa de fuente hasta flujo ahogado), `falla_sensor` (TB_Sensor_Fault programable), `transitorio_p1` (escalón de fuente). Alarmas ISA-18.2 derivadas del estado (SENSOR_FAULT p1, CAVITACION_CRITICA p2, DESVIACION_SP p3). 100% puro y determinista: sin timers ni relojes, base para la FMU de EP-05.
- **Contrato compartido** (`@sim/shared`): escenarios, `SimulationConfig` serializable (tipos planos), `SimSnapshot` (reloj de proceso, SP/PV/calidad, apertura/P_act, P1/P2, caudal, alarmas), protocolo discriminado por `type`: comandos `init`/`start`/`pause`/`reset`/`setSp`/`setScenario`/`exportRequest` y eventos `ready`/`tick` (con métricas computeMs/avgComputeMs)/`exported`/`error`.
- **Worker web** (`apps/web/src/sim/`): `simulation.worker.ts` (entry empaquetado por Vite con `new Worker(new URL(...), { type: 'module' })`) + `worker-loop.ts` (loop testeable con reloj y `post` inyectados; scheduling con `setInterval` a dt configurable, default 100 Hz; buffer de 10 000 snapshots para exportación CSV). `App.tsx` arranca el worker (init + start) y muestra un readout vivo mínimo (EP-04 reemplaza por el HMI).
- **Tests (Vitest, 22 nuevos: 11 physics + 11 web):** TC-NFUN-PERF-01 (10 000 pasos de 10 ms en ≈ 63 ms de wall-clock, umbral TC 20 s), TC-GEN-01 acotado (rampa SP 0→100→0 % a 0.5 %/s, 80 000 pasos, todos los valores finitos, lazo estable), TC-GEN-01a (protocolo completo del worker con reloj manual), determinismo/pureza del engine, escenarios (falla de sensor → BAD_SENSOR_FAILURE + alarma p1, cavitación → choked + alarma p2 con cota teórica de caudal, escalón P1), App con Worker mockeado (init+start, render de tick, terminate al desmontar).
- **Decisiones registradas:** snapshot en JSON plano (inspeccionable; Float32Array solo se justificaría con ancho de banda medido como problema); scheduling por `setInterval` simple — el reloj de proceso se acumula de los dt físicos, la deriva del timer solo añade jitter de cadencia, nunca corrupción de la física; App spawn worker como paso inicial del recorrido e2e (EP-07).
- **Métricas medidas:** TC-NFUN-PERF-01 ≈ 62.8 ms para 10 000 pasos (≈ 0.006 ms/paso, factor tiempo-real ≈ 1 590×; presupuesto TC: 20 s / ≥ 5×); computeMs por tick del worker reportado en cada evento `tick`.
- **Docs:** REQ-GEN-01 refinamiento + TC-NFUN-PERF-01, TC-GEN-01 (acotado), TC-GEN-01a en `docs/requerimientos.md`; `@sim/physics` y `@sim/shared` pasan a v0.4.0 (physics depende de shared por tipos).
- REQ/TC agregados: REQ-GEN-01 (refinamiento), TC-NFUN-PERF-01, TC-GEN-01 (acotado), TC-GEN-01a.

## v0.3.0 — EP-02: Transmisores inteligentes y sistema AMS `packages/physics` (2026-10-20)

- **REQ-FUN-TRM-01** — Transmisor con arquitectura de bloques Fieldbus/HART (`src/transmitter.ts`): Resource Block (tag, fabricante, modelo, serie, device status), Transducer Block (lectura primaria con `sensorBias` simulable, caracterización identity/sqrt, deriva térmica residual por °C, bandera `TB_Sensor_Fault`), Function Block AI (escalamiento LRV/URV, damping de primer orden con τ configurable, clamping 0–100% con limitStatus, `AI.PV` en unidades de ingeniería + % de escala con `AI.PV.Quality` GOOD/UNCERTAIN/BAD_SENSOR_FAILURE).
